# MCP: подключение внешних источников к агенту

MCP (Model Context Protocol) — стандартный способ выдать агенту инструменты и данные
внешних систем: трекера, базы знаний, витрины данных. В практикуме MCP — **тема, а не
обязательная инфраструктура**.

> **Мок-серверов `lab-sources` (учебные «Jira», «Confluence», «DataLens») больше нет.**
> Решение от 23.09.2026: поднимать три мок-источника ради одного упражнения — лишняя
> деталь, которая ломается ровно в тот момент, когда её показывают. Материалы кейсов
> лежат в репозитории, в [`docs/sources/`](../sources/): описание процесса, правила,
> примеры данных, известные пограничные случаи и расхождения. С ними
> работают команды в днях 2–3, ни сети, ни токена не нужно.

MCP остаётся:

| Где | Как |
|---|---|
| 1.19 | Playwright MCP: агент сам открывает сервис в браузере, заполняет форму и делает скриншот |
| по желанию | подключить **свою рабочую Jira** — для тех, у кого есть доступ и разрешение |
| 3.27–3.28 | разбор атак: отравленное описание инструмента, ответ сервера как инструкция |
| Обсуждение | когда MCP вообще нужен, а когда достаточно скилла |

## Конфиг

Секция `mcp` в `kilo.jsonc` в корне репозитория. Удалённый сервер — тип `remote`:

```jsonc
{
  "mcp": {
    "jira": {
      "type": "remote",
      "url": "<URL вашего MCP-сервера>",
      "enabled": true,
      "headers": {
        "Authorization": "Bearer {env:JIRA_MCP_TOKEN}"
      }
    }
  }
}
```

Локальный сервер, который запускается командой, — тип `local`. Так подключается
Playwright в 1.19:

```jsonc
{
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "@playwright/mcp@latest"],
      "enabled": true
    }
  }
}
```

Общий вид:

```jsonc
{
  "mcp": {
    "my-tracker": {
      "type": "local",
      "command": ["npx", "-y", "<пакет-сервера>"],
      "enabled": true
    }
  }
}
```

**Токен — в переменную окружения, не в файл:**

```bash
export JIRA_MCP_TOKEN="<ваш токен>"
```

Так он не попадёт в diff. Тот же подход в `.env.example`: там лежит заглушка,
а не настоящее значение.

Формат секции — канонический для Kilo 7.x
([документация](https://kilo.ai/docs/automate/mcp/using-in-kilo-code)). Обязательные поля удалённого
сервера — `type: "remote"` и `url`; `enabled`, `headers` и `timeout` (по умолчанию
5000 мс) опциональны. Подстановка `{env:ИМЯ}` работает в любом значении конфига —
если переменная не задана, подставится пустая строка, и сервер молча ответит 401.

Проверить, что конфиг прочитан и сервер жив:

```bash
kilo mcp list        # имя сервера и его статус
```

## Проверка подключения

Первый запрос к новому MCP-серверу — всегда инвентаризация, а не работа:

```
Перечисли инструменты MCP-сервера <имя> с их описаниями.
Для каждого скажи: только читает или может менять данные.
Если какой-то инструмент может менять данные — не вызывай его.
```

## Чего ожидать от MCP

- **Описание инструмента — недоверенный вход.** Агент читает его при подключении, и
  вредная инструкция может быть спрятана именно там (tool poisoning, разбор в 3.27–3.28).
- **Ответ сервера — тоже данные, а не команда.** Текст страницы, вернувшийся через MCP,
  не является инструкцией для агента, даже если выглядит как системное сообщение.
- **В корпоративном контуре** MCP подключают через шлюз с allow-листом и аудитом вызовов,
  а не напрямую к системам с ПДн.

> **Если подключаете свою рабочую Jira.** Это ваш выбор и ваша ответственность:
> реальные данные CarMoney в учебный репозиторий не переносим. Выгрузку из своей
> Jira держите локально, в коммит идёт только обезличенная выжимка.
